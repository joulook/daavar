# The benchmark book

One directory per benchmark, named as the paper's Table 1 names it, under the four groups the evaluation uses:

| group | what it holds | role in the paper |
|---|---|---|
| `synthetic/` | small programs whose behaviour is explained in a paragraph (naive, share, commit, chain, reset, width) | the idea works: violations found, conformance verified; the engines compared (stateless, stateful, offline); the validity argument |
| `application/` | bounded protocol models written against the Must API (two-phase commit, stores, locks, balancers, the re-modelled literature protocols), with a Java twin | refinement at larger scale, standalone and across languages |
| `realsw/` | real software (Raft, OmniPaxos) under the harness | refinement on real code |
| `agentic/` | the protocols implemented from their papers by context-free agents, in Java and in Rust, against the hand-written specification | the three-way check: specification against each implementation, and the two implementations against each other |

Inside a benchmark directory:

- `rust/`, `java/`: links to the sources under `benchmarks/<dir>/` (the Rust crate with its `spec` and `imp` entries; the Java program with its launcher class), where they exist.
- `README.md`: the communication model, the pairs (which variant is the implementation, which the specification), what each component does, how the variants differ, and why each pair conforms or violates.
- `EVAL.tex`, `EVAL.pdf`: every campaign run on the benchmark, one table per engine, generated by `scripts/bench-book.py` from the campaign CSVs (the same rows the paper's tables read) and brain-data. Blue rows are at the current engine pins; red rows are superseded and their rerun is pending; planned instances without a measurement are listed under "Not run".

Regenerate: `python3 -I scripts/bench-book.py <brain-data> <daavar> <PLDI/tex/tables> <group> --build` (the refresh loop does it every 30 minutes for the groups that exist).
