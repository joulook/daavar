# SwiftPaxos ballot-zero port

The source references below are paths under `code-src/`, with original line numbers. `INTERFACE.md` supplies the fixed roles, commands, entry point, setup, and quorums. Only c0 and c1 are visible. Both Program entries construct this same implementation; the harness supplies the specification.

## Roles and messages

- **c0, c1** use the interface's verbatim Req/Rep definitions and client function. Each sends one request and waits for its typed answer before continuing. Command identifiers are (client index, zero-based sequence). Writes set x and return Ack, Reads return Value(x), Rmw adds ten and returns Result(x). This replaces `state/state.go:14-33,115-146` as required.
- **init** sends Setup containing all addresses to replicas and libraries. Main starts n0, n1, n2, l0, l1, c0, c1 in that order, starts init, and joins. Main sends and receives no messages. Replicas explicitly queue messages preceding Setup. Libraries select tagged Setup, leaving any early untagged Req buffered in the Must mailbox.
- **l0, l1** propagate each request to all three replicas in index order (`client/client.go:175-195`). They accept only their command's n0 Reply plus either a matching checksum from n1's FastAckClient or a LightSlowAck from n1 or n2. They return the Reply's result once, discard late messages, and continue receiving forever after q replies (`swift/client.go:186-259`). While waiting for the next Req they selectively receive from their client; any late acknowledgments stay buffered until the following command's acknowledgment loop or the final drain. No other commands can be outstanding for that library.
- **n0** is leader for ballot 0. **n1** is the other fast-quorum member. **n2** does not originate FastAck. Every replica has its own register, dependency information, hash log, command descriptors, phases, and execution flags. There is no shared protocol state.
- **Propagate(id, command)** supplies the command; acknowledgments do not substitute for a missing proposal. Each replica computes dependencies and a checksum on proposal receipt, before handling the proposal (`swift/swift.go:274-286,767-791`).
- **FastAck(replica, id, dependencies, checksum, sequence)** goes to every other replica; the sender handles its own acknowledgment locally (`swift/swift.go:381-406`, `swift/batcher.go:122-142`). Only n0's sequence is significant. It increases on each n0 FastAck. A leader acknowledgment received before the proposal is saved; its processing waits for the proposal (`swift/swift.go:417-481,661-663`). Hash synchronization still occurs on receipt, or immediately after computing the proposal's original checksum if the proposal was absent (`swift/swift.go:278-282,293-298,794-820`).
- **FastAckClient(replica, id, checksum)** goes from n1 to the originating library. It omits dependency and sequence fields just as `swift/defs.go:62-67` and `swift/client.go:132-139` do. It is sent before n1's replica broadcast, following the unbatched order of `swift/batcher.go:122-142`.
- **Reply(id, checksum, result)** goes only from n0 to the originating library, after n0 executes (`swift/replychan.go:49-57`). The checksum is the one computed for that proposal, not a later synchronized log value. A Reply supplies the leader vote and returned value; it alone cannot answer a client.
- **LightSlowAck(replica, id)** is the slow acknowledgment, broadcast to other replicas and sent to the originating library. After a follower has the proposal and n0 FastAck, it sets ACCEPT, checks quorums, adopts the leader's dependencies if necessary and still undelivered, and sends LightSlowAck. It then counts its own slow acknowledgment if still undelivered (`swift/swift.go:428-479`). Receipt counts as a dependency-free acknowledgment (`swift/swift.go:524-530`).

## Commitment and execution

The replica fast certificate is n0 FastAck plus n1 FastAck with equal dependencies. The slow certificate is n0 FastAck plus a LightSlowAck from either follower. Votes are indexed by replica, so duplicates cannot enlarge a quorum. A pre-proposal acknowledgment can create a START descriptor; proposal processing enters PRE_ACCEPT for n0/n1; handling the leader enters ACCEPT; a certificate enters COMMIT (`swift/defs.go:25-30`, `swift/swift.go:368-369,428,499-520,665-684`). The leader vote is required even if two followers have voted (`replica/mset.go:45-84`). Nonempty but unequal follower dependencies do not count toward fast commitment. The source's distinction between nil and an empty dependency list is preserved semantically: ordinary FastAck has a concrete Vec, whereas LightSlowAck enters only the slow set. This avoids treating an empty ordinary FastAck as a slow vote.

A committed command executes once, when its proposal exists and every dependency has executed. n0 can also execute optimistically before handling its own FastAck (`swift/swift.go:398-406,533-556`). Execution retries after incoming messages and after predecessor execution, replacing successor goroutines and deliverChan (`swift/swift.go:510-520,558-565`). When several commands are enabled, nondet selects among them. No random generator or wall-clock scheduling is used. Processes remain in receive loops after the clients finish; main remains waiting for them.

Quorum callback execution is synchronous: commit calls execution before returning to dependency adoption, matching `swift/swift.go:453-463,499-520`. In particular, n2 initially has empty dependencies because its proposal handler returns before assigning proposeDep (`swift/swift.go:363-368`). If n2 already has a certificate when it handles n0's acknowledgment, the source can execute it using that empty dependency list before adopting the leader's list. This behavior is retained. Only n0 produces results for clients.

## Decisions and scope

1. **Flags fixed:** Exec=true, Dreply=true, optExec=true, fastRead=false, no configured slow addresses or proxies. The constructor exposes these options without fixing values (`swift/swift.go:106-107,129-150,392-404`); selecting optimistic execution is necessary for the requested leader Reply/client-ack flow (`swift/replychan.go:41-67`). Rmw is a writing command, including for dependency tracking. There is no separate read shortcut.
2. **Configured quorums:** FQ={n0,n1}; SQ includes all replica addresses and has size two. Thus both followers send slow acknowledgments even when dependencies agree: `replica/quorum.go:16-28` makes Majority.Contains always true, and `swift/swift.go:432-434` tests that membership. The checksum-mismatch-only LightSlowAck branch (`swift/swift.go:438-451`) is unreachable under this configuration because every follower already sends a slow acknowledgment. There is no invented choice between fast and slow: message arrivals determine which certificate wins.
3. **MSlowAck:** `swift/defs.go:69-75` defines it and `307,322` registers its channel, but the normal replica and client loops never receive that channel (`swift/swift.go:227-353`, `swift/client.go:117-184`). Normal slow processing uses LightSlowAck; this port does likewise, without inventing a full SlowAck transmission. MAccept is also omitted because its nonoptimistic/proxy route is disabled (`swift/replychan.go:41-67`).
4. **Dependencies:** retain the actual lightKeyInfo algorithm chosen by `swift/swift.go:778`: a Read depends on the last writing command; a writing command depends on the last command; each proposal replaces lastCmd, and a write also replaces lastWrite (`swift/key.go:101-137`). Rmw updates both. This preserves the source's compact dependency frontier rather than adding all prior conflicting commands or attempting to repair it. Read/Read do not directly depend on one another. Descriptors are retained indefinitely instead of recycling history slots (`swift/swift.go:745-756`, `swift/replychan.go:68-70`), and delivered messages are ignored.
5. **Checksums:** Path is the full ordered sequence of command IDs underlying the chained SHA-256 digest, starting from its zero initial state (`swift/dpath.go:60-88,145-162`). Equality compares these sequences, assuming no SHA-256 collisions; it preserves the ordered path information used by the protocol, including reads, which the hash implementation currently does not commute (`swift/dpath.go:26`). No cryptographic digest or hash cache is needed for invisible messages. Synchronization retains the highest leader sequence and its path, removes the acknowledged ID from the pending list, and recomputes the path by appending all remaining pending IDs (`swift/dpath.go:100-142`). Pre-proposal updates are buffered separately as in `swift/swift.go:794-803`. Original proposal checksums remain unchanged. Nil client checksums are represented by membership in the slow map, separately from the concrete empty path.
6. **Client matching:** use the unique configured fast quorum, resolving the explicit TODO about the correct majority in `swift/client.go:57-59`. Fast completion compares checksums, not dependencies (`swift/client.go:80-100`). Slow completion combines the nil-checksum leader copy and nil-checksum LightSlowAck (`swift/client.go:204-225,243-259`). The source's single c.val is stored per current command, which is equivalent under the mandated one-outstanding-command interface.
7. **Single event loop per process:** collapse command goroutines, sender, batcher, and reply goroutines into local handlers (`swift/swift.go:613-628,702-720`, `swift/batcher.go:23-253`, `swift/replychan.go:34-73`). A received message is processed through its local callbacks before the next receive. Cross-process events always use Must messages. Multiple enabled execution callbacks use nondet; otherwise arrival order determines behavior. Sends iterate fixed replica index order, like `replica/sender.go:151-165`. Broadcast excludes self because local calls already count self and the Go peer mesh does not establish a self connection (`replica/replica.go:137-157`).
8. **No batching/delays/timers/network/master/recovery:** mandated replacements. Individual FastAck and LightSlowAck messages replace MAcks/MOptAcks packing (`swift/batcher.go:29-142,144-250`). Ballot and sender checks are structural: all generated messages are ballot 0, leader fields are fixed to n0, and no failure/recovery messages exist. There are no retransmissions or timeouts.
9. **Arguments:** entry requires q>=1 and accepts the optional fifo/bag token. The harness's `--model` option selects delivery semantics; the optional program token is validated only. Both entries return the same implementation, as requested. Setup's tag separates internal library messages from the verbatim external Req type without wrapping observable requests.
